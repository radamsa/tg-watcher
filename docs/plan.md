# tg-watcher: план разработки

*Консольный клиент Telegram на Go · переработанная редакция · 23 ноября 2026*

## 1. Назначение

`tg-watcher` — консольный клиент Telegram для пользовательского аккаунта (не бот). Программа подключается к аккаунту, отслеживает новые сообщения в явно заданных каналах и группах и выводит их единым потоком в `stdout` в выбранном пользователем формате.

Основной сценарий — запустить процесс и наблюдать за сообщениями, поступающими с этого момента. Программа **не является архиватором**: она не сохраняет сообщения, историю или состояние мониторинга между запусками.

### 1.1. Ключевые правила работы

1. Мониторинг начинается только после состояния `READY`: авторизация завершена, чаты разрешены, начальные позиции мониторинга получены, обработчики и периодические проверки запущены.
2. Сообщения, существовавшие до начальной позиции мониторинга, не выводятся.
3. В пределах одного запуска программа старается восстановить сообщения, пропущенные из-за временного отключения сети.
4. Если штатное восстановление обновлений Telegram не может закрыть большой разрыв, программа дополнительно получает доступные сообщения через `messages.getHistory` и сразу выводит их. Это временное получение данных, а не хранение истории.
5. Сообщения и контрольные позиции мониторинга хранятся только в оперативной памяти. При завершении процесса они теряются.
6. После повторного запуска мониторинг начинается заново с новых начальных позиций. Сообщения, появившиеся во время выключенного приложения, намеренно не выводятся.
7. Вывод сообщений — единственная функция программы. Отправка сообщений, скачивание медиа и интерфейс вне CLI не входят в объём первой версии.

Гарантия доставки — **best effort в пределах доступных данных Telegram**, а не абсолютная гарантия отсутствия потерь. Если Telegram уже не предоставляет часть сообщений (например, они удалены или недоступны после слишком большого разрыва), восстановить их невозможно. Повторные события от live-потока и опроса должны дедуплицироваться.

## 2. Принятые решения

| Область | Решение |
|---|---|
| Язык и MTProto-клиент | Go, `gotd/td`, пользовательский аккаунт Telegram |
| Авторизация | Номер телефона, код Telegram, при необходимости облачный пароль 2FA |
| Начало мониторинга | После полной готовности (`READY`), а не при старте процесса |
| История до запуска | Не выводится и не сохраняется |
| Сообщения во время работы | Получение через Telegram updates; восстановление после разрывов; дополнительный опрос каналов |
| Долгий разрыв | Попытка backfill через `messages.getHistory` от последней обработанной позиции |
| Состояние | Только оперативная память; без БД и без постоянного хранилища update-state |
| Интервал опроса | 60 секунд по умолчанию, настройка в конфиге; рекомендуемый диапазон 30–60 секунд |
| Вывод | Сообщения — `stdout`; диагностика и ошибки — `stderr` |
| Форматирование | Один универсальный движок шаблонов; JSONL — именованный шаблон, не отдельный форматтер |
| Поля шаблона | `{datetime}`, `{channel}`, `{sender}`, `{text}` |
| JSON-экранирование | Фильтр `{field|json}` |
| Автор | `Имя Фамилия (@username)`; без username — имя; для анонимного сообщения — название чата либо пустая строка |
| Медиа | Текстовые заглушки; скачивания нет |
| Платформы | Linux, macOS, Windows; amd64 и arm64 |

## 3. Область первой версии

### 3.1. Поддерживается

- пользовательская авторизация Telegram;
- несколько заданных каналов, супергрупп и обычных групп;
- идентификаторы чатов, публичные `@username` и поддерживаемые ссылки `t.me`;
- новые сообщения после начальной позиции мониторинга;
- автор сообщения, если Telegram передал сведения об авторе;
- обычный поток обновлений Telegram и восстановление пропусков;
- периодический опрос целевых чатов для обнаружения сообщений, которые не поступают push-обновлениями;
- обработка текста, подписей и основных типов медиа через заглушки;
- пересланные сообщения;
- единый поток вывода;
- произвольные пользовательские шаблоны, в том числе JSONL.

### 3.2. Не поддерживается

- выдача старой истории при запуске;
- сохранение сообщений или контрольных позиций между запусками;
- отправка и редактирование сообщений;
- скачивание файлов и медиа;
- обработка изменений и удалений уже выведенных сообщений;
- секретные чаты;
- автоматическое вступление в каналы и группы по invite-ссылкам;
- темы форумов как отдельный объект мониторинга;
- несколько Telegram-аккаунтов в одном процессе;
- мониторинг всех подписок без явного списка (`--all`);
- TUI или GUI.

## 4. Командная строка

```text
tg-watcher <phone> [--format NAME] [--config PATH] [--password PWD] [--version] [--help] [--] <chat>...
```

- `<phone>` — номер в международном формате, например `+31612345678`.
- `<chat>` — один или несколько целевых чатов: числовой ID, `@username` или поддерживаемая ссылка `t.me`.
- Если список чатов пуст, программа завершается с кодом `2` и показывает краткую справку.
- `--format` — имя шаблона из конфигурации. Приоритет: CLI, `default_format`, встроенный `text`.
- `--config` — путь к TOML-файлу; по умолчанию `~/.tg-watcher/config.toml`.
- `--password` — облачный пароль 2FA. Приоритет: CLI, `TG_PASSWORD`, интерактивный запрос без эха, если `stdin` является терминалом. CLI-флаг не рекомендуется: аргумент может попасть в историю shell и список процессов.
- `--version`, `--help` — версия и справка.
- `--` завершает разбор флагов. Токены вида `-1001234567890` должны распознаваться как числовые ID чатов, а не как неизвестные флаги. Это поведение обязательно покрыть тестами.

Переменные окружения:

- `TG_API_ID` и `TG_API_HASH` — переопределяют значения Telegram API из конфига;
- `TG_PASSWORD` — облачный пароль 2FA.

### 4.1. Коды завершения

| Код | Значение |
|---:|---|
| `0` | Штатное завершение по Ctrl+C либо закрытие `stdout` (EPIPE/SIGPIPE) |
| `1` | Необработанная ошибка во время работы |
| `2` | Ошибка аргументов или конфигурации |
| `3` | Ошибка авторизации или потеря авторизации |
| `4` | Ни один из заданных чатов не удалось разрешить или открыть |

Если часть чатов недоступна, программа предупреждает об этом в `stderr` и продолжает работу с доступными. Код `4` используется только тогда, когда не осталось ни одного доступного целевого чата.

## 5. Авторизация и безопасность

1. Для подключения нужны `api_id` и `api_hash`, полученные пользователем на `my.telegram.org`.
2. Первый запуск: ввод номера, кода подтверждения Telegram и, если требуется, облачного пароля 2FA.
3. Сессия сохраняется отдельно для каждого номера в `~/.tg-watcher/sessions/`.
4. Каталог сессий имеет права `0700`, файл сессии — `0600`. Права проверяются при запуске; слишком широкие права приводят как минимум к предупреждению, а невозможность обеспечить безопасное хранение — к отказу от записи сессии.
5. Коды подтверждения и пароль 2FA не записываются в логи и не включаются в диагностические сообщения.
6. Предпочтительные способы передачи 2FA-пароля — `TG_PASSWORD` или интерактивный ввод без эха. `--password` оставляется как необязательный, но небезопасный с точки зрения утечки через shell/process list вариант.
7. Сессионный файл даёт доступ к аккаунту. Его нельзя коммитить, публиковать или передавать другим лицам.
8. Не логировать `api_hash`, код подтверждения, пароль 2FA, содержимое сессионного файла и полное содержимое сообщений.

Обрабатываемые ошибки авторизации: неверный номер, неверный код, неверный пароль, истёкший/отозванный auth key, `FLOOD_WAIT`. Для `FLOOD_WAIT` выдерживать время, сообщённое сервером; не выполнять агрессивные повторы.

## 6. Конфигурация

Формат — TOML. Встроенный шаблон `text` работает без пользовательского файла конфига. Другие именованные шаблоны, включая `jsonl`, описываются тем же способом.

Пример `~/.tg-watcher/config.toml`:

```toml
default_format = "text"

[telegram]
api_id = 12345
api_hash = "0123456789abcdef"

[watch]
# Период проверки каждого целевого чата через messages.getHistory.
# 60s по умолчанию; рекомендуется не задавать меньше 30s.
poll_interval = "60s"

# Размер одной страницы API-запроса. При большом количестве сообщений
# между проверками выполняется постраничная загрузка.
poll_page_size = 100

[formats.text]
template = "[{datetime}] [{channel}] [{sender}] {text}"
datetime_format = "2006-01-02 15:04:05" # Go layout
timezone = "local"                     # local, UTC или зона IANA
multiline_indent = 4

[formats.jsonl]
# Это обычный шаблон. Отдельной реализации JSONL в приложении нет.
template = '{"datetime":{datetime|json},"channel":{channel|json},"sender":{sender|json},"text":{text|json}}'
datetime_format = "2006-01-02T15:04:05Z07:00"
timezone = "local"
```

Правила:

- `api_id` и `api_hash` можно переопределить через переменные окружения.
- При отсутствии пользовательского конфига доступны встроенные параметры формата `text`; Telegram API credentials всё равно должны быть заданы.
- `[formats.<name>]` задаёт именованный шаблон. Поле `template` обязательно.
- Для всех шаблонов используется один движок. Отдельного поля `type` и реестра форматтеров не требуется.
- `[watch].poll_interval` по умолчанию `60s`. Значение должно быть корректной длительностью Go; минимально допустимое значение — `30s`, чтобы не создавать чрезмерную нагрузку на API.
- `[watch].poll_page_size` по умолчанию `100`; значение валидируется в пределах, допустимых реализацией и API.
- Неизвестное поле, пустой шаблон, неизвестный плейсхолдер/фильтр, некорректная зона или формат времени дают ошибку до подключения к Telegram и код завершения `2`.
- Если пользовательский шаблон `text` или `jsonl` определён, он переопределяет встроенный шаблон с тем же именем.

## 7. Универсальные шаблоны вывода

### 7.1. Плейсхолдеры

| Плейсхолдер | Значение |
|---|---|
| `{datetime}` | Время сообщения в заданной временной зоне и формате |
| `{channel}` | Отображаемое название канала или группы |
| `{sender}` | Автор сообщения в согласованном формате |
| `{text}` | Нормализованный текст сообщения с маркерами вложений и пересылки |

Для шаблонов JSON поддерживается фильтр `{field|json}`. Он кодирует значение как JSON-строку целиком, включая внешние кавычки и экранирование управляющих символов. Например:

```toml
template = '{"channel":{channel|json},"sender":{sender|json},"text":{text|json}}'
```

Кавычки вокруг `{text|json}` в шаблоне добавлять нельзя: фильтр уже возвращает JSON-строку вместе с кавычками.

### 7.2. Синтаксис и валидация

- Разрешённые поля: `datetime`, `channel`, `sender`, `text`.
- Разрешённый фильтр первой версии: `json`.
- `{unknown}` и `{field|unknown}` — ошибка конфигурации.
- Для вывода буквальных фигурных скобок предусмотреть экранирование `{{` и `}}`.
- Парсер шаблона компилируется при загрузке конфига; при обработке каждого сообщения не нужно повторно разбирать шаблон.
- Подстановка выполняется по белому списку, без `text/template`, выражений, вызовов функций или произвольного доступа к данным.

### 7.3. Поле `sender`

Формирование автора:

1. Если известен обычный пользователь — `Имя Фамилия (@username)`.
2. Если username отсутствует — `Имя Фамилия`.
3. Если Telegram передал подпись автора публикации (`post_author`) — использовать её, когда обычный автор не определён.
4. Для анонимного сообщения использовать название канала/группы; если определить источник нельзя — пустую строку.

Не подменять неизвестного автора именем владельца аккаунта или случайным участником чата.

### 7.4. Нормализация текста и медиа

Значение `{text}` одинаково для всех шаблонов:

- текстовое сообщение — исходный текст;
- фото — `[photo]` и подпись, если она есть;
- видео — `[video]` и подпись;
- документ — `[document]` и подпись;
- голосовое сообщение — `[voice]`;
- аудио — `[audio]`;
- стикер — `[sticker]`;
- опрос — `[poll]` и доступный текст/вопрос;
- геолокация — `[location]`;
- контакт — `[contact]`;
- пересланное сообщение получает префикс `[fwd: источник]`;
- альбом выводится отдельными записями — по одной на каждое сообщение альбома.

Медиа не скачивается. Если Telegram не передал подпись или сведения об авторе, не пытаться получать их дополнительными запросами без необходимости.

### 7.5. Вывод

- `stdout` содержит только записи сообщений.
- Диагностика, предупреждения, состояние подключения и ошибки идут в `stderr`.
- Запись выводится целиком, с построчным flush после успешной записи.
- В шаблоне `text` многострочный текст продолжается с отступом `multiline_indent`.
- В JSONL переводы строк и управляющие символы экранируются через фильтр `json`, поэтому одно сообщение занимает одну физическую строку.
- Закрытый pipe (`EPIPE`/`SIGPIPE`) считается штатным завершением. Прочие ошибки записи в `stdout` приводят к коду `1`.
- Запись в `stdout` выполняется одним writer-компонентом, чтобы несколько обработчиков не перемешивали фрагменты строк.

## 8. Работа с чатами

### 8.1. Поддерживаемые идентификаторы

- числовой ID Telegram, в том числе Bot API-вид `-100…`;
- `@username`;
- публичная ссылка вида `https://t.me/<username>` и ссылка на конкретное сообщение, из которой можно извлечь username;
- ссылка вида `t.me/c/...` — только если соответствующий чат уже доступен аккаунту и может быть найден среди диалогов.

Invite-ссылки (`t.me/+…`, `joinchat`) не должны автоматически приводить к вступлению в чат. Для первой версии такие ссылки отклоняются с понятным сообщением.

### 8.2. Разрешение и доступ

1. Разрешить идентификаторы в peer/input peer Telegram.
2. Получить актуальные access hash и сведения, необходимые для вызова методов Telegram.
3. Проверить, что пользовательский аккаунт имеет доступ к чату.
4. Удалить повторы в переданном списке целей.
5. Недоступные чаты пропустить с предупреждением в `stderr`.
6. Если не осталось ни одного доступного чата — завершить программу с кодом `4`.

Нельзя считать Bot API ID внутренним MTProto ID без преобразования и проверки. Преобразование числового идентификатора должно опираться на тип peer и сведения из диалогов аккаунта.

## 9. Архитектура

### 9.1. Пакеты

```text
cmd/tg-watcher/       точка входа
internal/cli/         разбор аргументов, коды выхода
internal/config/      загрузка TOML, defaults, валидация
internal/auth/        авторизация, 2FA, сессионное хранилище
internal/telegram/    адаптер над gotd, API интерфейсы для тестов
internal/resolve/     разрешение ID, username и ссылок в peer
internal/watch/       запуск мониторинга, update recovery, poller, состояние чатов
internal/message/     независимая модель сообщения и нормализация Telegram updates
internal/format/      компиляция и применение универсальных шаблонов
internal/output/      единая последовательная запись в stdout
internal/logging/     логирование только в stderr
```

Внутренние пакеты приложения не должны зависеть от сгенерированных типов gotd напрямую, кроме адаптера `internal/telegram`. Это упрощает тестирование и локализует изменения API библиотеки.

### 9.2. Поток данных

```text
Telegram MTProto updates ─┐
                          ├─> фильтр целевых чатов
messages.getHistory poll ─┘          │
                                     v
                         нормализация в Message
                                     │
                                     v
                     дедупликация и порядок по чату
                                     │
                                     v
                         универсальный шаблонизатор
                                     │
                                     v
                          единый stdout writer
```

Один источник события — обычный MTProto update; второй — периодический опрос `messages.getHistory`. Оба источника должны попадать в один pipeline и использовать одинаковую модель сообщения и одинаковую дедупликацию.

### 9.3. Модель сообщения

Минимальная внутренняя модель:

```go
type Message struct {
    ChatID    int64
    MessageID int
    Date      time.Time
    Channel   string
    Sender    string
    Text      string
}
```

В форматтер передаются только поля, предусмотренные шаблонами. `ChatID` и `MessageID` нужны для фильтрации и дедупликации и не обязаны выводиться пользователю.

### 9.4. Состояние в памяти

Для каждого целевого чата хранить только данные, необходимые для текущего запуска:

- peer и access hash;
- начальную позицию мониторинга;
- последнюю обработанную/проверенную позицию сообщений;
- состояние периодического опроса и backoff;
- ограниченное состояние дедупликации по `(ChatID, MessageID)`.

Не хранить текст сообщений, полную историю, PTS и контрольные позиции в пользовательской БД или постоянном файле. Для gotd `updates.Manager` использовать in-memory state и не подключать постоянное `Storage` для update-state. Файл авторизационной сессии — отдельное исключение: он необходим для повторного входа и не содержит архив сообщений.

### 9.5. Получение и восстановление обновлений

Использовать `gotd/td/telegram/updates` (`updates.Manager`) как механизм управления последовательностью MTProto updates:

- подключить manager как `UpdateHandler`;
- подключить update middleware согласно документации версии gotd, чтобы менеджер видел ответы RPC;
- использовать `updhook.AffectedHook`, если приложение вызывает методы, изменяющие PTS;
- запускать `gaps.Run` после авторизации;
- состояние менеджера держать в памяти;
- корректно зарегистрировать/инициализировать отслеживаемые каналы и access hash при старте;
- не считать простой callback `UpdateHandler` достаточным механизмом восстановления пропусков.

При сетевом разрыве `updates.Manager` должен восстанавливать common/channel differences через `updates.getDifference` и `updates.getChannelDifference`, повторяя постраничные запросы до актуального состояния. Для `FLOOD_WAIT` и временных RPC-ошибок использовать backoff, не блокируя весь процесс без необходимости.

### 9.6. Важный нюанс каналов, которые не присылают push-updates

Telegram не гарантирует push-доставку новых публикаций из каждого канала в каждую пользовательскую сессию. По документации gotd, его idle-проверка channel difference для таких каналов выполняется примерно раз в 15 минут. Поэтому один update stream не обеспечивает требуемую оперативность.

Реализовать дополнительный `Poller` на базе пользовательского API `messages.getHistory`:

- запускать его после готовности мониторинга;
- по умолчанию проверять каждый целевой чат раз в `60s`;
- разрешать настройку интервала в конфиге, минимальное значение — `30s`;
- запрашивать только сообщения с ID больше последней проверенной позиции (`min_id`), не перечитывая всю историю;
- размер страницы по умолчанию — до 100 сообщений; если новых сообщений больше, загружать страницы до полного закрытия диапазона;
- Telegram возвращает сообщения в обратном хронологическом порядке; перед выводом восстановленные сообщения одного чата отсортировать по возрастанию ID/времени;
- после успешной обработки диапазона передвинуть cursor; при частичной ошибке не передвигать его за непрочитанный диапазон;
- распределять запросы по времени и ограничивать параллелизм, чтобы не создавать всплеск запросов при большом числе чатов;
- соблюдать `FLOOD_WAIT` и применять per-chat backoff.

Опрос не должен запускаться как неконтролируемый бесконечный цикл запросов. Методы Telegram ограничены серверными лимитами; более частый опрос повышает нагрузку и вероятность `FLOOD_WAIT`.

### 9.7. Обработка слишком большого разрыва

Если gotd сообщает `updates.channelDifferenceTooLong`, использовать callback `OnChannelGap` и выполнить backfill через `messages.getHistory` для соответствующего чата, начиная с последней обработанной позиции.

- Загрузить доступные сообщения страницами.
- Отфильтровать сообщения, уже выведенные из update stream или периодического опроса.
- Вывести оставшиеся сообщения в хронологическом порядке.
- Не сохранять текст или историю на диск.
- Если Telegram не возвращает весь диапазон, сообщить об этом в `stderr`, вывести доступные сообщения и продолжить мониторинг с актуальной позиции.

`ChannelDifferenceTooLong` не следует трактовать как гарантированную потерю всего диапазона: это сигнал, что обычный difference больше не может вернуть все обновления с переданного PTS. Дополнительная выборка истории — попытка восстановить сообщения, которые ещё доступны через API.

### 9.8. Начальная граница `READY`

Порядок запуска:

1. Загрузить и полностью проверить конфигурацию и шаблоны.
2. Создать защищённое хранилище сессии и авторизоваться.
3. Разрешить все заданные чаты и получить необходимые peer/access hash.
4. Создать update manager и зарегистрировать обработчики до начала приёма целевых событий.
5. Инициализировать состояние отслеживаемых каналов актуальными данными диалогов/peer; не восстанавливать сообщения, созданные до начального состояния мониторинга.
6. Для каждого целевого чата получить начальный message ID (`messages.getHistory`, `limit=1`) и установить начальный cursor. Само это сообщение не выводить.
7. Запустить обработку updates и Poller, проверить готовность всех внутренних компонентов.
8. Перейти в `READY`, вывести служебное сообщение о готовности только в `stderr`.

До `READY` обработчики не должны писать сообщения в `stdout`. События, накопленные до начальной позиции, отбрасываются. Для нескольких чатов Telegram не предоставляет атомарный общий snapshot; поэтому техническая граница задаётся отдельным начальным cursor каждого чата, полученным в фазе подготовки непосредственно перед `READY`.

При повторном запуске начальные cursor создаются заново. Старые update-state и message cursor с диска не загружаются.

### 9.9. Дедупликация и порядок

Ключ сообщения: `(ChatID, MessageID)`.

- Update stream и Poller направляют события через общий механизм дедупликации.
- Обработка сообщений одного чата сериализуется, чтобы пересекающиеся запросы и update callbacks не приводили к гонкам при продвижении cursor.
- Восстановленные страницы одного чата сортируются по возрастанию ID до передачи в writer.
- Нормальный update stream использует упорядочивание gotd; приложение не должно самостоятельно подменять PTS-механику простым сравнением message ID.
- Состояние дедупликации хранится только в памяти и должно иметь ограничение по объёму.
- Не обещать глобальную строгую сортировку сообщений разных чатов по времени: единый live-поток отражает порядок фактической доставки/обработки. Восстановленные сообщения каждого конкретного чата упорядочиваются.

## 10. Завершение и устойчивость

- Использовать `context.Context` от `signal.NotifyContext` для Ctrl+C/SIGTERM.
- При завершении остановить Poller, отменить запросы, остановить update manager и корректно закрыть writer.
- Все фоновые goroutine должны иметь явный жизненный цикл; не оставлять бесконечные фоновые задачи после отмены context.
- Очередь сообщений между обработчиками и writer должна быть ограниченной. При заполнении применять backpressure, а не молча отбрасывать сообщения; поведение при невозможности продолжить обработку фиксировать в диагностике.
- Ошибки отдельного чата (например, потеря доступа) не должны останавливать мониторинг остальных чатов.
- Потеря авторизации — фатальная ошибка с кодом `3`.
- Ошибка записи в stdout из-за закрытого pipe — штатное завершение; прочие ошибки записи — код `1`.
- Ошибки периодической проверки одного чата логировать с ограничением частоты, чтобы не засорять `stderr`.

## 11. Тестирование

### 11.1. Модульные тесты

**CLI и конфигурация**

- разбор номера, флагов, нескольких целей, `--` и отрицательных ID `-100…`;
- отказ при пустом списке чатов;
- приоритет `--format` / `default_format` / `text`;
- приоритет параметров 2FA;
- defaults и переопределение TOML;
- валидация poll interval, page size, timezone и datetime layout.

**Шаблоны и сообщения**

- компиляция и валидация плейсхолдеров;
- `{field|json}` для кириллицы, кавычек, обратных слешей, табуляции и переводов строк;
- round-trip JSON через `encoding/json`;
- буквальные скобки `{{` и `}}`;
- многострочный текст и отступы;
- все типы медиа, подписи, пересылки и альбомы;
- имя автора с username, без username, `post_author`, анонимный автор и неизвестный источник.

**Мониторинг**

- до `READY` ни одно сообщение не попадает в stdout;
- сообщения с ID не выше начального cursor не выводятся;
- обычное новое сообщение выводится один раз;
- одно сообщение, одновременно полученное из update stream и Poller, выводится один раз;
- Poller использует `min_id`, загружает несколько страниц и не пропускает сообщения при размере выборки больше page size;
- частичная ошибка пагинации не продвигает cursor за неполный диапазон;
- после краткого обрыва update manager восстанавливает пропущенные обновления;
- `ChannelDifferenceTooLong` запускает backfill через `messages.getHistory`;
- недоступные/удалённые сообщения приводят к предупреждению, но не к падению всего процесса;
- повторный запуск начинает новый baseline и не выводит сообщения, появившиеся до него;
- `FLOOD_WAIT` вызывает ожидание/backoff;
- заполнение очереди не приводит к молчаливой потере записей;
- Ctrl+C, SIGTERM, EPIPE и ошибки stdout обрабатываются ожидаемо.

Для тестов Telegram API использовать интерфейс-адаптер и fake API/clock. Тесты конкурентного доступа запускать с `go test -race ./...`.

### 11.2. Интеграционные сценарии

На отдельном тестовом аккаунте:

## 12. Этапы разработки

**Готово, когда:** CLI-тесты проходят; ошибки аргументов дают понятные сообщения и корректные коды.

### Этап 2. Конфигурация и шаблонизатор

**Готово, когда:** текстовый и JSONL-примеры реализованы только конфигурацией; модульные тесты проверяют валидацию и JSON round-trip.

### Этап 3. Авторизация и сессии

Вход по номеру, code/2FA, безопасное хранилище сессий, обработка ошибок Telegram.

**Готово, когда:** первый вход и повторный запуск проходят на тестовом аккаунте; права каталога и файла соответствуют требованиям.

Разбор ID/username/ссылок, проверка доступа, получение начальных message ID, модель состояния чата, переход в `READY`.

**Готово, когда:** недоступные чаты пропускаются; сообщения до начального cursor не выводятся; при отсутствии доступных чатов возвращается код `4`.

### Этап 5. Live updates и нормализация сообщений

Подключение `updates.Manager`, регистрация обработчиков, фильтрация чатов, нормализация текста/медиа/автора/пересылок, общий event pipeline.

**Готово, когда:** новые сообщения поступают в правильный внутренний pipeline; восстановленные update batches не дублируются; нет прямой зависимости форматтера от типов gotd.

### Этап 6. Poller и backfill

Периодический `messages.getHistory` с `min_id`, постраничное чтение, сортировка, общий dedup, `OnChannelGap` для `ChannelDifferenceTooLong`, настройка интервала и backoff.

**Готово, когда:** новые сообщения из непушимых каналов обнаруживаются в пределах интервала опроса плюс времени ответа API; пропуски после сетевого разрыва восстанавливаются в пределах доступности Telegram; повторные записи от двух источников не выводятся в штатном сценарии.

### Этап 7. Устойчивость и корректное завершение

Backpressure, writer, сигналы, EPIPE, обработка ошибок чатов, ограничение логирования, race-тесты.

**Готово, когда:** приложение корректно завершается и не теряет сообщения молча при заполнении внутренней очереди.

### Этап 8. Релиз и документация

GoReleaser, бинарники, README, инструкции по API credentials, безопасности сессии, конфигурации и примеры конвейеров.

## 14. Риски и ограничения

1. **Ограничения Telegram API.** Частый опрос большого числа чатов увеличивает нагрузку и вероятность `FLOOD_WAIT`. Использовать интервал не меньше 30 секунд, ограничивать параллелизм и соблюдать серверные задержки.
2. **Не все каналы присылают push-updates.** Это причина отдельного Poller; задержка обнаружения зависит от интервала опроса и доступности API.
3. **Большой разрыв обновлений.** `ChannelDifferenceTooLong` может означать, что полный диапазон обновлений уже нельзя получить через difference. Backfill через `messages.getHistory` восстанавливает только те сообщения, которые ещё доступны.
4. **Отсутствие постоянного состояния.** После остановки/перезапуска пропуски не восстанавливаются — это сознательное продуктовое решение.
5. **Дедупликация ограничена текущим процессом.** Между запусками она не работает и не должна работать.
6. **gotd — низкоуровневая библиотека с API, который может меняться.** Версия фиксируется; интеграция с update manager и middleware проверяется на конкретной версии.
7. **Сессия равна доступу к аккаунту.** Обязательны права `0700`/`0600`, защита от публикации и отсутствие секретов в логах.
8. **Порядок между разными чатами.** Строгая глобальная сортировка невозможна без дополнительной задержки/буферизации; гарантируется порядок восстановления внутри каждого чата, а live-поток отражает фактическую обработку событий.
9. **Вывод в pipe.** Медленный потребитель stdout способен замедлить приложение; требуется ограниченная очередь и backpressure.

## 15. Вопросы, оставленные за рамками принятой спецификации

Следующие решения не являются блокирующими для первой реализации и не должны расширять объём работ автоматически:

- фильтрация сообщений по отправителю или ключевым словам;
- отдельный режим только входящих или только исходящих сообщений;
- отображение ID чата/сообщения и ссылки на сообщение как дополнительные плейсхолдеры;
- фильтрация служебных событий группы;
- отдельные шаблоны для разных чатов;
- динамическое добавление чатов без перезапуска.
